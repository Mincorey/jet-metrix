## 1. ⚙️ Архитектура и Структура Данных

Приложение JetMetrix разработано как SPA на **React 19 (TypeScript, TailwindCSS v4, Vite)** с серверной частью на **Vercel Serverless Functions** и базой данных **Supabase (PostgreSQL)**.

### 🗄️ Схема Базы Данных (14 Таблиц)
1. **`Employees`** — Учет сотрудников (авиатехники, старшие авиатехники, администраторы), их PIN-коды для авторизации и архивные даты.
2. **`Workdays`** — Учет рабочих смен. Содержит агрегированные поля заправки/приема для сменных отчетов (заполняются в момент закрытия смены).
3. **`Fuel_Reception`** — Журнал внутренних приемов топлива в резервуарный парк.
4. **`Fuel_Reception_Auto`** — Журнал приемов топлива из автоцистерн (АЦ).
5. **`Fuel_Dispensing_TZA`** — Журнал выдачи топлива со склада в топливозаправщики (ТЗА).
6. **`Fuel_Dispensing_VS`** — Журнал выдачи топлива из ТЗА в воздушные суда (ВС) с номерами контрольных талонов и паспортов.
7. **`Trains`** — Журнал замеров прибывших ЖД-цистерн (вагонов).
8. **`Daily_Measurements`** — Журнал суточных замеров резервуаров (уровень, объем, масса, плотность, температура).
9. **`In_warehouse`** — Журнал внутрискладских перекачек топлива между резервуарами.
10. **`Monthly_Inventory`** — История ежемесячных инвентаризаций.
11. **`Tanks_Directory`** — Справочник резервуаров с калибровочными (градуировочными) таблицами в JSON.
12. **`TZA_Directory`** — Справочник топливозаправщиков с объемом и флагом мониторинга остатка.
13. **`Tech_Lines`** — Справочник технологических линий.
14. **`Settings`** — Глобальные параметры системы (названия, настройки Telegram-уведомлений, логотип).

## 2. 🚨 Критические Баги и Логические Ошибки в Расчетах

В ходе детального анализа серверного и клиентского кода были обнаружены критические ошибки, которые приводят к искажению финансово-технического учета, сбоям в работе приложения и неработоспособности системных функций.

### ✅ [ИСПРАВЛЕНО] Баг №1: Полная потеря данных приемов из АЦ в сменных отчетах (Workday Closing)
* **Файл:** [`api/_handlers/workdays/close.ts`](file:///c:/PROJECTS/JET-METRIX/api/_handlers/workdays/close.ts#L20-L22)
* **Суть проблемы:**
  При закрытии смены итоговый объем принятого топлива рассчитывается как сумма внутреннего приема, автоприема и перекачек. Однако автоприем (`Fuel_Reception_Auto`) запрашивается по условию:
  ```typescript
  supabase.from('Fuel_Reception_Auto').select('Volume, Mass, Date').eq('Date', workday?.Date ?? '')
  ```
  В таблице `Fuel_Reception_Auto` поле `Date` сохраняется со временем (например, `"10.06.2026 14:15"`), тогда как `workday.Date` содержит только дату (`"10.06.2026"`). Соответствие по `.eq` **никогда не срабатывает**.
* **Результат:** Суммарные объемы принятого топлива за смену (`Fuel_Received_L` и `Fuel_Received_KG`) рассчитываются неправильно (показывают заниженные показатели, игнорируя АЦ).
* **Связанный баг:** В POST-обработчике автоприема [`api/_handlers/fuel-reception-auto.ts`](file:///c:/PROJECTS/JET-METRIX/api/_handlers/fuel-reception-auto.ts) поле `Workday_ID` вообще не записывается в БД (хотя в схеме колонка есть и с фронтенда оно могло бы передаваться).

### ✅ [ИСПРАВЛЕНО] Баг №2: Полный крах функции резервного копирования (Backup)
* **Файл:** [`api/_handlers/backup.ts`](file:///c:/PROJECTS/JET-METRIX/api/_handlers/backup.ts#L18)
* **Суть проблемы:**
  Для экспорта данных бэкап-обработчик циклически обходит все таблицы и пытается отсортировать их по ID:
  ```typescript
  const { data } = await supabase.from(table).select('*').order('id' as any)
  ```
  Однако в таблице **`Settings`** первичным ключом является `key` (тип `TEXT`), а колонки `id` **не существует**.
* **Результат:** Запрос к `Settings` падает с ошибкой PostgreSQL `column "id" does not exist`, возвращая клиенту `500 Internal Server Error`. Резервное копирование полностью сломано.

### ✅ [ИСПРАВЛЕНО] Баг №3: Ошибки в определении последней операции (Edit/Delete Last Operation)
* **Файл:** [`api/_handlers/operations/last/[workdayId].ts`](file:///c:/PROJECTS/JET-METRIX/api/_handlers/operations/last/%5BworkdayId%5D.ts#L25-L27)
* **Суть проблемы:**
  При запросе последней операции для редактирования/удаления код проверяет `Workday_ID` для всех таблиц, кроме `Trains` и `In_warehouse`:
  ```typescript
  if (table !== 'Trains' && table !== 'In_warehouse') {
     query = query.eq('Workday_ID', workdayId)
  }
  ```
  Поскольку `Fuel_Reception_Auto` не сохраняет `Workday_ID` (Баг №1), запрос `.eq('Workday_ID', workdayId)` для этой таблицы всегда возвращает пустой массив.
* **Результат:** Прием из автоцистерны никогда не отображается как «Последняя операция», из-за чего оператор не может отменить или скорректировать его в случае ошибки. Кроме того, для `In_warehouse` и `Trains` (у которых есть колонка `Workday_ID`) фильтрация по смене игнорируется на уровне БД, что при большом числе транзакций может выдать некорректную операцию из чужой смены.

### ✅ [ИСПРАВЛЕНО] Баг №4: «Зависание» смен при переходе через полночь (Midnight Crossing)
* **Файл:** [`src/data/WORKDAY.ts`](file:///c:/PROJECTS/JET-METRIX/src/data/WORKDAY.ts#L31-L33)
* **Суть проблемы:**
  При инициализации приложения открытая смена ищется с фильтрацией по сегодняшней дате:
  ```typescript
  const openWorkdays = allWorkdays.filter(
    w => w.Workday_Status === 'Open' && w.Date === todayStr
  );
  ```
  Если смена авиатехника начинается в 20:00 (June 9) и длится до 08:00 (June 10), то после 00:00 значение `todayStr` меняется на `"10.06.2026"`. Смена, открытая с датой `"09.06.2026"`, перестает загружаться в приложении на планшете.
* **Результат:** Авиатехник посреди ночи «теряет» свою открытую смену на экране устройства. Система предлагает открыть новую смену, что приводит к разрыву транзакций, дублированию записей и хаосу в отчетах.

### ✅ [ИСПРАВЛЕНО] Баг №5: Исчезновение ночных транзакций из хронологии (Timeline)
* **Файл:** [`api/_handlers/dashboard/timeline/[workdayId].ts`](file:///c:/PROJECTS/JET-METRIX/api/_handlers/dashboard/timeline/%5BworkdayId%5D.ts#L20-L30)
* **Суть проблемы:**
  Для построения таймлайна смены транзакции запрашиваются из БД с использованием текстового префикса даты смены (например, `Date LIKE '09.06.2026%'`).
* **Результат:** Если смена переходит через полночь, то все операции, совершенные после 00:00 (получившие дату следующего дня), не попадают под маску и полностью исчезают из хронологии текущей рабочей смены.

### ⚠️ Недочет №6: Потенциальный сбой при сохранении ЖД-цистерн (Trains)
* **Файл:** [`api/_handlers/trains.ts`](file:///c:/PROJECTS/JET-METRIX/api/_handlers/trains.ts#L23-L29)
* **Суть проблемы:**
  POST-запрос пытается вставить поле `Density_20` (плотность при 20°С). Однако в SQL-схеме таблицы `Trains` поле `Density_20` отсутствует. В зависимости от строгости настроек PostgreSQL на стороне Supabase, попытка вставить несуществующую колонку может приводить к ошибкам записи. При этом ключевые поля `Workday_ID` и `Timestamp` при вставке игнорируются.

## 3. ⚠️ Риски Производительности и Избыточный Трафик

Некоторые архитектурные решения в коде представляют серьезную угрозу для производительности и приведут к зависанию приложения по мере накопления истории транзакций.

### ✅ [ИСПРАВЛЕНО] Угроза №1: Полная загрузка БД на клиенте в отчетах (Full-Table Client Filtering)
* **Файлы:** 
  * [`src/components/ShiftReport.tsx` (функция `getDateBasedReport`)](file:///c:/PROJECTS/JET-METRIX/src/components/ShiftReport.tsx#L54-L62)
  * [`src/components/FuelDispensingVSReport.tsx`](file:///c:/PROJECTS/JET-METRIX/src/components/FuelDispensingVSReport.tsx#L27-L41)
  * [`src/components/FuelDispensingTZAReport.tsx`](file:///c:/PROJECTS/JET-METRIX/src/components/FuelDispensingTZAReport.tsx#L27-L41)
  * [`src/components/reports/FuelReceptionAutoReport.tsx`](file:///c:/PROJECTS/JET-METRIX/src/components/reports/FuelReceptionAutoReport.tsx#L26-L44)
* **Суть проблемы:**
  Для построения отчета за определенный день приложение отправляет GET-запрос без параметров, скачивая **абсолютно всю историю** приемов, выдач и перекачек из базы данных, а затем фильтрует массивы локально на устройстве с помощью JS `.filter()`.
* **Риск:** Уже через год работы база данных разрастется до десятков тысяч записей. Скачивание мегабайтных массивов JSON на мобильные планшеты через сотовую связь в аэропорту приведет к падению производительности, долгой загрузке экранов и высокому расходу мобильного трафика.

### ✅ [ИСПРАВЛЕНО] Угроза №2: Полная загрузка БД в Dashboard Summary
* **Файл:** [`api/_handlers/dashboard/summary.ts`](file:///c:/PROJECTS/JET-METRIX/api/_handlers/dashboard/summary.ts#L44-L52)
* **Суть проблемы:**
  Для расчета KPI дашборда серверный обработчик запрашивает все строки из 5 таблиц операций без ограничений по дате, а затем фильтрует их по таймстампу в цикле:
  ```typescript
  if (ts < periodStartTs || ts > periodEndTs) return
  ```
* **Риск:** Функция Vercel Serverless имеет лимит по памяти (128-256 MB) и времени выполнения (10-15 сек). Из-за отсутствия SQL-фильтрации (`WHERE "Timestamp" >= ...`) по мере роста базы данных обработчик будет падать по таймауту.

### ✅ [ИСПРАВЛЕНО] Угроза №3: Линейное замедление расчета остатков резервуарного парка (Park State)
* **Файл:** [`api/_handlers/park-state.ts`](file:///c:/PROJECTS/JET-METRIX/api/_handlers/park-state.ts#L56-L61)
* **Суть проблемы:**
  Для расчета текущего объема каждого бака запрашиваются все автоприемы (`Fuel_Reception_Auto`) по имени резервуара без ограничений, после чего в оперативной памяти происходит фильтрация:
  ```typescript
  const filteredRecAutoRows = (recAutoRows || []).filter(r => parseRuDateTime(r.Date) > lastMeasTimestamp)
  ```
* **Риск:** Каждое открытие карты парка нагружает сервер парсингом дат для сотен старых строк автоприема.

### ✅ [ИСПРАВЛЕНО] Угроза №4: Внутренний HTTP-петлевой вызов (Loopback HTTP Request)
* **Файл:** [`api/_handlers/telegram/webhook.ts`](file:///c:/PROJECTS/JET-METRIX/api/_handlers/telegram/webhook.ts#L53-L57)
* **Суть проблемы:**
  При обработке команды `/stock` бот отправляет реальный HTTP-запрос `fetch` на собственный адрес `/api/park-state` для получения данных парка.
* **Риск:** Это вызывает «холодный старт» вложенной серверной функции, удваивает время ожидания пользователя в Telegram и может привести к сбою, если переменная `VERCEL_URL` настроена некорректно или требует авторизации.
